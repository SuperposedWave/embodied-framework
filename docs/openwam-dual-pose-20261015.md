# OpenWAM旧双臂配置：公共位姿标准化说明

范围仅为原有 OpenWAM-Alpha-Sim-RoboTwin-Full 权重与 RoboTwin 链路。新配置不替代历史配置，不更换模型、归一化统计、控制器或评分，不代表阶段4验收通过或契约冻结。

## 1. 到底修了什么

新增模型输入输出配置 `eef20_dual_wxyz_encoded_absolute`。名字中的 `eef20` 表示双臂共20个模型原生数值：每只手3个位置数、6个旋转表示数、1个夹爪数。`absolute` 表示输出的是世界坐标系下的绝对位姿，而不是相对移动量。

新配置使用同一份权重，但把模型内部特殊编码还原为明确的公共物理位姿。输出包含左右两条 `PoseTarget`（末端目标）和左右两条原生夹爪请求；不再用一个原生16维数组代表两只手的位姿。

旧 `eef20_dual_legacy` 配置、`dual-eef16-legacy-quaternion@1` 协议、0.1入口及历史结果保留。公共契约字段和 Runner 没有修改；Runner是只负责通用调用顺序、预算和证据的执行循环。

## 2. 输入端和输出端分别核实

`xyzw` 是向量分量x、y、z在前、实数分量w在后；`wxyz` 是w在前。六维旋转不是六个角度，而是3×3旋转矩阵的前两列，每列3个数。

| 边界 | 固定源码实际做的事 | 新配置怎么处理 |
| --- | --- | --- |
| 环境观测 | `get_arm_pose`调用`get_*_ee_pose`，最终用`transforms3d.mat2quat`生成wxyz | Benchmark Adapter原本就把它重排为公共xyzw；保留实际数值 |
| 原生数据写入 | HDF5写入器原样保存`endpose`，不重排四元数。HDF5是训练轨迹的数据文件格式 | 不改数据写入器，也不改历史数据 |
| 训练读取 | `_read_eef_actions`将保存的四个数直接交给“按xyzw读取”的六维旋转转换 | 明确记录：wxyz数值在模型内部被当作xyzw编码 |
| 归一化与80维排列 | 原始20维先按匹配统计归一化，再映射到模型内部80维；输入和动作共用这套处理 | 完全留在原生模型端，不进入公共协议 |
| 推理输入 | 原生客户端也将环境wxyz数值直接交给同类xyzw转换；它先转float32再计算旋转 | 公共xyzw先恢复成wxyz数值，再调用固定原生函数，保持权重原先收到的输入 |
| 模型动作解码 | 六维旋转经原生解码得到一组“名义xyzw”数值，但它属于上面的训练编码 | 将这四个数按物理wxyz解释，再重排为公共xyzw |
| 环境执行 | `take_action(action_type="ee")`取出每只手7个位置/朝向数；后续`quat2mat`按wxyz解释朝向 | Benchmark Adapter将公共xyzw重排回环境wxyz，继续用原控制器执行 |

这不是根据函数名字作判断：检查了实际分量提取、旋转矩阵计算、原始数据写入，以及控制器调用。固定上游的部分注释称环境数据是xyzw，与实际实现不符；没有修改这些只读文件。

### 用“没有旋转”解释这次转换

真实没有旋转的公共四元数是 `(0,0,0,1)`。环境原生wxyz写法是 `(1,0,0,0)`。原训练编码却把后一个数组按xyzw处理，所以模型内部的旋转表示看起来像“绕x轴转180度”。

这时不能把模型内部的旋转直接贴上公共朝向标签，否则会真的误报成180度旋转。新 Adapter先还原这套编码，公共朝向仍然是没有旋转；环境收到的原生数组也保持不变。

这里没有先假设“两个错误抵消”。已经使用固定上游函数检查无旋转、三个轴各90度和180度、一般旋转，并检查保存的真实动作。结论只适用于具名配置及其固定来源，不能推广到所有OpenWAM权重。

## 3. 排列问题不等于坐标或工具参考点问题

本轮不改变世界坐标系，不增加机器人底座平移，不添加模型侧逆运动学，也不重新定义工具位置。逆运动学是由目标末端位置计算关节目标，仍由环境处理。

实际观测来自 `_trans_endpose(is_endpose=False)`，不是 `get_*_tcp_pose` 取得的夹爪中心。源码已经应用原生 `global_trans_matrix` 与 `delta_matrix`，它们是环境已有的末端方向校准；ALOHA配置中还有原生夹爪偏移参数。

执行端仍保留 `_trans_from_gripper_to_endlink` 的工具到末端连杆转换，以及规划器的世界到机器人底座转换、`frame_bias`平移校准和左右臂小角度校准。没有把这些处理当成四元数重排，也没有在模型端重复处理。

公共动作记录的是控制器被要求执行的、以世界坐标表示的位置和朝向，工具参考点沿用环境的原生定义。不能把它与夹爪中心或裸连杆的姿态混为一谈，也不能把发出的目标当成下一步一定测到的姿态。此次不新增跨工具参考点的自动重定向。

原公共状态来源描述中“native TCP position”容易让人误以为它来自夹爪中心访问器。本轮把来源文字更正为实际的`get_arm_pose/get_ee_pose`路径；状态数值、历史目标标识和原生执行行为不变。TCP在这里指工具参考点，不是任意两个名为“末端”的位置都相同。

## 4. 为什么夹爪仍保留原生请求

保存的111条真实动作中，有8条的夹爪请求略超出0到1。例如`1.00390625`或`-0.00390625`。这不是合法的公共夹爪开度。

原控制器先按请求值插值，再在每个物理步截断。若在Model Adapter里提前截断，会改变原生轨迹。因此新配置复用已有的 `gripper-open-fraction-interpolate-then-clamp@1` 协议：两个位姿完全标准化，只有两个夹爪请求保留具名原生扩展。

环境增加具名执行格式 `dual-cartesian-native-gripper@1`，表示“左右绝对位姿加左右原始夹爪请求”。它复用已有命令类型和控制器，要求两只手、两个夹爪完整绑定；不放宽公共合法开度范围，不新增公共契约字段。

## 5. 转换证据与软件回归

新配置：[可执行示例](../examples/mn_openwam_dual_wxyz_encoded_absolute.json)。示例使用现有固定任务、相同种子入口和指令协议，预算限制为4次环境动作及4次模型调用；不是完整任务成功率评测。

以下float32指32位浮点数，即原生动作使用的数值精度。公共格式保留其数值，重新排列四元数时不额外归一化或重算它。

- [改前基线](../outputs/openwam-dual-pose-baseline-20261015-before/baseline-check.json)：390项测试和CLI `0/0/0/1/2`通过。
- [转换核验](../outputs/openwam-dual-pose-mapping-20261015-run2/receipt.json)：113组保存的真实观测，完整模型输入与固定原生规则一致；111条保存的真实动作，公共位姿往返后的原生16维动作逐数值、逐类型完全一致。
- 使用固定控制器纯转换函数比较的位置/朝向解释不变；旋转矩阵差异为0。该门禁未创建SAPIEN场景、未运行IK或GPU推理。SAPIEN是本项目使用的物理仿真运行库。
- [实际SAPIEN Pose接口核验](../outputs/openwam-dual-pose-sapien-api-20261015-run1/receipt.json)：无旋转、三个轴各90度和180度、一般旋转共8类全部确认wxyz语义。没有创建场景；矩阵最大分量差约`1.2×10⁻⁷`，属于该接口float32数值表示的舍入。
- 8类已知旋转经固定上游转换后，最大旋转矩阵分量误差约`6.6×10⁻⁸`；四元数整体取反仍视为同一个旋转。
- 上游训练读取与推理输入原本存在float32量化顺序差别，113组数据最大差约`8.4×10⁻⁸`。这是两条原生函数路径的差别，不是新Adapter造成的变化；新推理输入与原生推理规则严格一致，不能把训练比较描述成逐字节相同。
- 新增26项合成测试，覆盖旋转、两只手、非法输入、夹爪越界请求、原生精度、模型侧缓存和取图节奏，以及公共观测的排列与实际计数。
- [最终修改后基线](../outputs/openwam-dual-pose-baseline-20261015-final2/baseline-check.json)：416项通过，五组CLI退出码仍为`0/0/0/1/2`。这是软件回归，不是真实模型任务成绩。

首次离线核验的失败回执保留在`openwam-dual-pose-mapping-20261015-run1`：诊断比较器用float32和float64两种算术精度分别归一化相同四元数，产生了比较差异。修正为同精度比较数学朝向后通过；没有改生产动作，也没有降低原生动作逐值一致的门禁。

### 差异究竟在哪里

- 初始状态、原图和第一步执行结果完全相同。
- 前两次模型输入完全相同。四次原始模型动作回复也全部相同，不能把本轮轨迹差异归因于模型新动作的随机性。
- 第二步执行后的状态和原图开始不同；当步物理步数仍相同。第三、四次输入的图像和状态因而已不同，但本轮这两次服务回复仍相同；没有核实服务器实际前向次数，不能据此推断模型忽略图像。
- 第三步物理步数差1，第四步差6，最终原生参考比框架少5个物理步。因此严格全轨迹复现为false，不用容差或任务成败把它改成通过。
- 已将首个差异定位在原生规划/物理执行之后，而不是这次四元数转换或模型原始输出。当前证据没有逐物理步的规划轨迹和积分中间量，尚不能进一步断定是规划器还是物理积分造成的差别。本轮不改变这两个组件来追齐历史。
