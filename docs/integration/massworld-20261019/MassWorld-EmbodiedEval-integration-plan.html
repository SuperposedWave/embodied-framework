MassWorld × EmbodiedEval 0.3 整合方案

2026年10月19日 · 基于用户上传的MassWorld快照和当前0.3代码 · 待确认方案，不是已合并交付。

结论：能合并，但先分层接通

推荐把 MassWorld 作为统一项目入口，把 EmbodiedEval 作为机器人评测执行内核。先接通、验证，再合到同一个仓库；不同时重写两套模型/环境Adapter。

人话就是：MassWorld负责“选什么、安排哪次评测、保存和展示结果”；EmbodiedEval负责“机器人每一步看见什么、模型输出什么意思、动作怎么执行和怎么判分”。最终用户从一个入口使用，不需要在两套系统之间手工搬配置或结果。

这不是永远保留两个独立产品：可以形成一个MassWorld仓库、多个职责明确的Python包。一个仓库不等于一个巨大的Python环境，也不等于两套循环同时控制机器人。

本轮只是方案和只读核实，不实施合并，不创建平台任务，不更改0.3契约、上游、历史结果或Git提交。

两边现有能力如何分工

方面MassWorld / WorldEvalKit现状整合后归属
总体平台MassWorld根目录以目标架构文档为主，实际可复用实现主要在WorldEvalKit。没有把目标门户、部署注册、统一控制平面当作已实现。统一入口、任务计划、运行身份、产物与展示由MassWorld一侧组织；网页管理台如需要，单独建设。
离线评测已有图像/视频生成、评分、typed Artifact与阶段编排。Artifact是带类型名的数据或文件容器。原流程保留，不强迫视频模型输出机器人动作。
机器人执行既有EpisodeRunner和原生整批任务流程；语义、计数和协议与我们的0.3不完全一致。接入EmbodiedEval的机器人任务只由其0.3 Runner推进仿真。原生整批入口另标模式保留。
模型与环境接入双方已有各自注册/声明。我们的模型与环境独立维护，当前有11份模型输入输出配置、7份环境协议。当前机器人领域以EmbodiedEval注册表为唯一实现源，外层只导出目录元数据，不复制推理或控制代码。
运行环境WorldEvalKit支持本地/Conda/venv/container等组织；remote枚举存在，但对应通用执行分支拒绝。轻量编排与模型/仿真原生环境继续隔离，不宣称已有通用远程执行能力。
平台算力qz Provider仍属目标设计；本机现在有可用qz工具。后续新增一个平台调度适配器，只负责提交/查询/日志/停止，不解释机器人动作。

目标结构：上层统一，内层只有一个执行者

MassWorld 统一入口与任务计划（需扩展后端选择）
├─ WorldEvalKit 原有离线生成/评分
├─ WorldEvalKit 原有具名原生整批协议
└─ EmbodiedEval 0.3 执行后端（新增桥接包）
   ├─ 独立模型注册 → Model Adapter
   ├─ head/关节/位姿等公共观测与类型化公共动作
   ├─ 独立环境注册 → Benchmark Adapter
   └─ 0.3 Runner：唯一推进仿真、计数和调用评分的循环

运行方式：先本地执行器；后接启智平台执行器
共同记录：计划身份、执行尝试、来源摘要、指标和证据索引

Adapter指某一侧的格式转换组件；Runner指调用顺序、预算和计数循环；后端指上层可调用的一套执行能力，不要求新增网络服务。

外层可以显示每一步的进度，但不再调用WorldEvalKit的EpisodeRunner去包住我们的Runner，不二次分割动作缓存，不重复reset/step，不接管控制器或评分。

真正需要新增的桥接点

不是装上一个现成插件就自动完成。WorldEvalKit现有插件入口只有模型和Benchmark两类；EvaluationRunner构造时就实例化其模型/环境，Planner先按它的protocol和Port绑定，再调用自定义build_plan。仅加一个Stage并不能绕过前面的类型要求。

推荐给上层新增一个小而明确的“执行后端”入口。在实例化原有ModelAdapter之前，先确定本次任务走哪个后端；未选择新后端的原流程保持不变。新插件名和方法都属于拟议接口，不是现有功能：

拟议接口具体作用不承担什么
catalog()：组件目录从0.3双方注册表分别读取能力、输入输出配置、环境协议、资产与真实验证状态。不生成模型×环境组合工厂；不把DreamZero登记状态显示成真实验证通过。
preflight()：运行前检查构造严格0.3配置并调用现有预检查；返回缺相机、坐标、单位、关节或资产等原因。不能仅凭Artifact类型名或训练机器人名判断可组合；必要输入不自动猜补。
build_plan()：上层阶段计划生成检查、整次运行、结果整理三个阶段，连接既有Stage/Handler扩展能力。不把每条机器人动作拆成上层Stage；不继承动作重试。
execute()/import_result()：执行与结果导入在明确的原生环境中启动0.3入口，将退出码、manifest、逐回合结果和证据登记到外层。不在模型Adapter里接收环境对象；不重算官方成功条件。

可以拟议新增worldevalkit.execution_backends扩展入口，其中embodied-v03选择桥接包；点号表示扩展入口的命名空间。这是上层新增接口，不是把机器人契约改成0.4。

若暂时不能改MassWorld核心，可先把0.3作为独立外部任务调用并导入报告，但此时只能称“任务级联通”，不能称模型目录与规划已经全面统一。不要用predict抛NotImplemented的占位ModelAdapter充当已完成接入。

源码依据：WorldEvalKit/registry.py; runner.py; adapter.py:13–14,157–197; 65–76,211–223; 326–335；原文与行号见代码证据。

公共空间怎么合，不再重复写Adapter

机器人领域继续以现有0.3为公共标准。环境原生相机先映射到head/wrist/left_wrist/right_wrist等公共字段；模型Adapter从公共字段取值。图像缩放、状态编码、归一化和动作缓存仍由模型侧处理；控制器、逆运动学、仿真和评分仍由环境侧处理。

公共位置用米、时间用秒，朝向用明确坐标系下的xyzw四元数：向量分量x/y/z在前、实数分量w在后。坐标转换需要真实变换与工具参考部位，不因字段统一而凭空获得标定。未知物理含义的原生数组只能走同名协议扩展。

MassWorld的Artifact当外层文件/数据容器，里面可以存0.3的序列化记录或完整证据包。校验仍调用0.3语义校验器，不能只包一个type_id就声称完成物理映射。机器人观测不强迫与视频生成输入共用一个扁平数组。

新模型或环境只接入0.3一份实际Adapter；MassWorld目录从它自动导出。外层目录项是选择和展示，不是第二份推理实现。已有MassWorld视频模型仍走原离线后端；已有原生服务模型若要改成公共动作，必须另行核实权重与动作含义、补真实转换和测试。

首版桥接直接传配置与落盘结果，不逐帧经HTTP上传大图，也不实现远程DataRef载荷读取。DataRef是外部数据引用；能管理结果文件不等于会读取实时图像引用。

配置、版本和来源如何统一

用户最终只选一次模型、环境、任务和预算。下面仅是拟议的上层选择示意，不是当前可直接运行的配置，也不代表已经选定真实试点：

execution_backend: embodied-v03
model:     现有模型ID + 具名输入输出配置 + 固定权重来源
benchmark: 现有环境ID + 具名协议 + 固定环境来源
episodes:  明确任务、初始化、seed和预算
control:   有多个可用控制格式时明确选择

桥接层将它解析成现有严格RunConfig；不存在的顶层字段不直接塞进0.3 JSON，也不静默丢弃。最终解析配置、代码提交、权重和归一化摘要、环境与控制器版本、初始化身份都进入运行清单。

至少区分三种身份：计划指纹表示“想运行什么”；执行尝试ID表示“这一次真实启动”；平台job_id表示“启智承载它的任务”。相同配置再次运行要有新的执行尝试与输出目录，不能用配置哈希掩盖重复执行。桥接索引关联两边run_id、episode_id、观测和命令编号。

大型权重沿用有依据的内容摘要，不降级成文件大小/修改时间。资产位置通过新运行配置显式解析；合仓不全局替换旧证据中的绝对路径，也不复制大权重、虚拟环境或原始结果进Git。

源码依据：WorldEvalKit/runner.py; benchmarks/_robotics.py:78–99; 23–35；原文与行号见代码证据。

指标与错误不能在合并时走样

后端事实外层应显示禁止的转换
正常执行，success=false且valid=true运行完成、任务未成功；保留原始布尔值与评分来源。当作CLI失败或把有效失败丢出统计分母。
Metric.value=null、valid=false评分不可用，并显示原因。填0，冒充失败成绩或做进总平均。
退出码1或框架/评分错误框架或评分异常，保留最后确认计数和证据。当成模型任务失败。
退出码2，预检查拒绝配置/结构不满足，未作为有效试验。记录成模型失败的一次已完成试验。
进程被杀、动作已发但无确认取消/执行状态未知，保留最后确认事件；不能给出可靠完整评分。自动补造动作数、成功值，或原地重试该动作。
导入旧结果或缓存命中历史证据导入/结果复用，标明原运行身份。显示为本次新推理。

WorldEvalKit当前EvaluationResult.metrics只收数值且拒绝布尔值；我们的Metric还包含valid、单位、来源和不可用原因。首版不必改其数值表：有效数值做展示投影，完整原始指标放samples/产物；成功布尔值保留，若显示0/1须另标“显示投影”，不是更改官方评分。

统计必须同时报告计划、启动、完成、有效评分、成功、异常和未知数量。成功率分母遵循具名协议；若只算有效评分子集，必须标明覆盖率与子集范围，不能冒充完整任务集成功率。

执行异常后也要先持久化后端日志/部分证据与错误清单，再把失败传给外层；不能因为Stage失败就把唯一排错证据丢掉。首版不在导入阶段重新调用官方评分器。

缓存、恢复、超时与并发的边界

机器人场景会改变状态。动作已经执行、回执丢失后再试一次，可能真的多走一步。外层的通用能力不能未经适配就成为机器人能力。

  • 整次机器人运行默认只尝试一次：Stage使用Retry(attempts=1)、Cache(enabled=False)，并关闭该路径的reuse_results/resume；不能只关一层缓存。
  • 不从中断回合续跑。不恢复模型缓存、随机状态和仿真状态，就不能宣称有恢复能力。明确的新试验用新ID、完整重新初始化，不能伪装为原尝试的延续。
  • 保留现有合作式预算检查；不因上层RuntimeExecutor能杀进程就宣称Runner获得硬超时。任何外部终止都按证据完整性标记取消或执行未知，新的取消协议需单独确认。
  • 首版仍串行验证，避免共享GPU、模型服务和仿真对象互相污染。后续若并行，按相互隔离的完整试验调度，不在两个循环里并行发动作。
  • 现有动作缓存、取图节奏、物理步数/原生动作数/仿真秒数三个计数，以及测量状态和控制目标区分全部保留。

源码依据：WorldEvalKit/contracts/plan.py; execution.py; runner.py:9–43; 99–111,405–460; 416；原文与行号见代码证据。

启智平台放在哪一层

平台执行器只负责“把已确定的评测计划交给哪台机器”，不负责机器人语义。本机qz已能发现接口且登录此前已验证；本轮只再次读取版本和操作schema，没有读取账号资料、列举任务或创建任务。

拟议执行器能力当前可用API定义实施时仍需验证
提交完整试验qz train CreateJob工作区/项目/计算组/镜像/挂载/GPU字段、权限、资源费用与任务启动命令。
查询与日志qz train GetJob / GetJobLog调度中、运行、退出和业务错误的精确映射；日志分页与脱敏。
停止自有试验qz train StopJob目标确属本次试验，用户授权停止；平台停止不等于已安全回收机器人执行状态。
防止自动重跑CreateJob定义有auto_fault_tolerance及重试相关字段明确关闭平台自动容错并检查生效值；无法证明不重跑时不宣称安全恢复，不自动重发超时提交。

这四项是API定义可用，不是已完成提交/停止实测。原草案使用旧qzcli 0.3.0的create/status/watch等命令，当前安装为qz v1.0.0动态service/action接口，不能复制旧命令。schema检查回执见只读定义核对。

平台凭据由CLI正常登录管理，不进入模型配置、评测清单、Git或报告。依然只在当前命令范围处理代理。GPU总体平均20%的既有目标沿用，但占卡负载单列，不作为评测工作量；本轮无GPU评测或新平均值声明。

先保留EmbodiedEval现有包布局，减少原生子进程入口、相对资源和测试路径的额外变化。Git导入保留已有提交与标签，不把权重、环境和历史大产物搬成源码。历史路径保持原样，新运行使用新位置配置。

同名RoboDojo/RoboTwin组件按backend、固定revision、任务协议和难度区分，不能互相覆盖注册。MassWorld快照的RoboTwin hard是demo_randomized，现有后端常用demo_clean；RoboDojo版本也不同，先并列保留，不能拼成同一条成功率。

合仓前还要核对发布权限和第三方声明：附件根目录有MIT文本、WorldEvalKit有Apache-2.0文本；本项目当前未见顶层LICENSE。不能据此自动给全部内容统一换许可证。保留各组件来源与NOTICE，公开分发范围需所有者确认。
