EmbodiedEval 0.3 · 2026年10月23日（北京时间）
状态：待确认的设计方案。仅新增评审材料，尚未修改契约、Adapter、Runner或现有评测设置。

核心结论与范围

采用你的优先级：具体 Benchmark 评测协议的明确要求优先；协议允许模型决定的部分，沿用匹配权重的原生部署设置。框架负责把两边声明核对成一份可追溯、可执行的计划，不自行创造全局频率。

这里的 Benchmark 不是单独一个名字，而是固定版本、赛道、任务范围、机器人、控制器和评分设置组成的具名协议。同一个环境可以既有严格复现协议，也有允许模型自选部署参数的协议。环境能运行某个设置，不代表该设置自动满足某一正式榜单要求。

本方案覆盖：物理步长与动作推进规则的身份核对、模型观测要求、动作批次消费、重新决策和缓存归属。动作批次就是 action chunk，即一次预测得到的一串动作；“执行条数”是重新请求动作前使用其中多少条。它与仿真物理计算次数、图像采集次数、真实模型生成次数都不同。

假设各模型已有对应任务的微调权重，但不因此假设所有权重的时间含义已核实。首轮不做动作插值、重复动作、自动改控制频率、额外取图、实时异步、硬仿真时间上限或自动调参；不新增训练任务。

按每个参数判断优先级

不能把整个 Benchmark 简单标为“固定”或“灵活”。例如它可以固定动作周期，却允许模型选择每次执行几条。每个参数分别保存规则、适用范围和来源，再联合检查是否能同时满足。

规则性质如何选最终值停止／限制条件
Benchmark 明确固定采用规定值或规定的执行策略；允许把模型配置调整到这个值，但只能用它确实支持的方式。模型不支持则报不兼容；不强行裁切隐藏缓存、重复动作或改变权重。
Benchmark 明确允许范围／若干选项使用范围内、匹配权重的模型原生设置；用户以后明确选择的新实验值也必须在范围内。原生值越界则要求选择一份明确支持的具名设置；不自动取最接近值或取上限。
Benchmark 明确交给策略自行决定采用模型侧的原生执行条数、批次／融合策略和缓存归属。仍须满足环境实际接口、必要观测、动作语义、预算和其他协议限制。
只有参考程序默认值，没有强制说明复现这份参考程序时沿用其值，记为“参考默认”，不能升级成全 Benchmark 的硬规定。若另选设置，单独记为新实验；是否可用于正式榜单仍待核。
规则没有说明／来源未核实现有原生参考复现可以保持原行为，但标明规则未核实；不自动当成自由配置。不能宣布正式协议合规。缺少执行必需语义时直接拒绝，而非仅给警告继续。

明确要求优先，不意味着框架有能力把不兼容变兼容。如果环境固定每0.05秒一条，而权重明确需要每0.1秒一条，本轮应拒绝该受检协议；调整动作时间或重新适配权重是另一项工作，不能靠“Benchmark优先”一句话跳过。

来源须区分官方规则、官方参考实现、模型发布配置和用户自定义实验。若同一协议的文档与代码冲突，先记录冲突，不擅自解释成允许调整。我们自行制定的受控协议可以固定参数，但必须标为本项目实验，不能冒充官方新增规定。

保持模型与环境独立接入

保留 M+N 架构：M 是模型数量，N 是环境数量，每个组件只实现自己的 Adapter。新增以下拟议声明和通用核对逻辑，不为每个组合新增 Python 工厂或白名单。

拟议组件保存／负责什么不做什么
Benchmark 的执行限制声明协议身份；各参数是固定、范围可选、策略自定、参考默认还是未知；相应值、来源及适用范围。不按模型名称选择规则，不从模型例程默认值推导官方硬限制。
模型的执行能力与偏好声明权重身份；预测批次长度；原生执行条数／完整批次／融合方式；可调整范围；缓存归属和原生配置入口；动作时间已知或未知。不接收环境对象，不按 Benchmark 名称分支，不用未核实的训练帧率填动作时长。
通用执行策略解析器按优先级合并两边声明，检查全部约束，生成最终计划或明确拒绝原因。解析器是核对元数据的程序。不处理图像、不归一化、不改动作、不做机器人控制，不猜未公开规则。
最终执行计划逐项列出选定规则、为什么采用、谁负责落实、来源、待核事项，以及是否改变原生设置。不是一份新的逐对接线脚本，也不是正式验收证书。
Runner 与证据保存按通用顺序调用组件，保存计划、动作、时间和请求边界，核对可观测的执行反馈。不偷偷绕过原生缓存强制重新推理，不把每次 predict 调用算成一次真实模型生成。

一次运行的完整流程

  1. 选择具名 Benchmark 协议和具名权重配置，加载各自的声明与来源。
  2. 在不启动GPU推理的预检查中生成“声明层面计划”，显示采用值、适用范围、缺口与冲突；未知项不伪装为已验证。
  3. 运行初始化时再次核对环境实际控制周期与组件实际配置；静态声明可能被运行环境覆盖，不能只检查一次。
  4. 由组件把计划落实到自己的原生设置：模型侧只调自己支持的参数，环境侧保持自己的协议。服务无法确认所选设置时，不把本地配置声明当成服务已生效。
  5. 执行中保存真实动作及请求边界；配置、声明和实际行为不符时报告违规／未知状态，不在中途自动换设置或重发动作。
  6. 输出结果时分别报告规则核查、实际落实、原生复现差异和任务成绩。

对于隐藏缓存的服务，外层调用5次接口不一定触发新生成。要满足“每5条重新决策”的协议，模型侧必须能够真正配置并验证这一行为；单纯丢掉外层队列尾部不构成正确实现。只应有一个实际消费规则的管理者。

如果原方法本身采用每步融合等策略，记录并复用该策略，不能强行解释成“固定若干步后丢掉尾部”。首轮不新增自动根据任务表现或耗时调整执行长度的算法。

需要补的契约缺口与影响

当前0.3契约已有物理／控制周期、真实采集时间、观测历史要求，以及模型原生动作时间与缓存归属说明；现有时间扩展明确仅处理观测，不调整动作消费。仍缺三项类型化声明：

  • Benchmark 对执行设置的约束：硬规定还是允许选择、取值范围、适用版本／赛道及依据。
  • 模型实际能调整什么：生成长度与消费长度分开，原生偏好、可支持集合、服务内部缓存及配置落实方式。
  • 两者核对后的最终计划：选定值、理由、落实方、待核项，以及声明与实际验证的区别。

建议以0.3的具名、显式可选执行策略扩展提交评审，具体字段与兼容方式在实施前定稿。本文件不是新增字段已经生效，不直接升级0.4，也不把现有观测时间扩展解释成已支持动作调度。

实施预计涉及公共声明、配置校验、预检查回执、运行计划与诊断，以及原生已有可调参数的透传。无需更改公共位姿／关节物理含义，也不修改图像处理、归一化、权重、控制器、IK或官方评分。

旧0.3配置默认保持当前原生行为，旧报告和历史路径不回写。新严格规则检查显式启用；未启用的新旧原生运行不能因此被标成已获正式合规认证。不能借兼容模式绕过已经明确冲突的严格协议，也不恢复0.1／0.2入口。

实施顺序与验收

以下是待确认的后续工作，每个阶段交付证据后再确认进入下一阶段。本轮没有开始其中的代码实施。

建立规则账本和声明方案

逐项覆盖现有五类环境和13份具名配置，分别登记物理／动作推进、观测、执行条数和重新决策规则；补充来源、适用范围、未知项与冲突。定稿可选扩展的字段、默认行为和序列化兼容方案，不改任何实际运行设置。验收重点是“参考默认”和“强制规则”没有混淆。

实现通用解析和合成检查

实现独立声明、通用解析器、预检查和计划保存，不启动真实模型。覆盖固定值、范围、策略自定、参考默认、未知、相互矛盾及运行值漂移；检查模型无法截短、生成长度不足、历史缺失、变时长误用和双重缓存。两个测试模型与两个测试环境验证交叉组合，再增加第三方无需修改其他Adapter；明确标为合成架构测试。

接通原生可调入口并验证

先接通源码明确支持的参数，把计划交给对应组件而不是由Runner改动作。使用保存样本验证输入、动作值、精度、缓存与取图边界；再按确认范围做有限步真实对照。若新参数确实改变重新推理位置，单独记录新实验，不拿新动作与旧动作不同作为必然映射错误，也不靠任务成功代替验证。

验证中保留现有主634项、桥接34项及五组CLI退出码0／0／0／1／2无回归要求，并新增执行策略测试；这些数字是当前已记录基线，不是本轮重新运行结果。旧原生差异、DreamZero后置硬件和全任务覆盖待办不被本方案自动关闭。后续GPU验证另按阶段确认，沿用既有资源上限与利用率记账规则。

每次结果应交付什么证据

  • 规则身份及来源、模型权重与具名配置、最终执行计划及所选理由。
  • 声明是否满足限制、实际配置是否落实、是否仍是原生复现：三项分别报告。
  • 实际执行动作数、物理步数、仿真时间、请求动作批次的位置、真实图像采集时间、剩余缓存与停止原因。
  • 接口调用、动作请求和真实模型生成分开计数；生成次数无法核实就保留未知。
  • 官方指标、任务失败、基础设施错误和执行状态未知分开记录；规则核查通过不等于榜单正式接收，也不等于阶段验收通过。
